# TZXDATA — техническое задание на систему параметров BobrovXDATA

**Проект:** acadPaletteSetXDATA — панель свойств объектов AutoCAD на основе схемы параметров.
**Основание:** [задача #17](https://github.com/veb86/acadPaletteSetXDATA/issues/17), исходное [ТЗ](TZ.md),
выполненные этапы 1–5 (см. [README](README.md)).
**Платформа:** AutoCAD 2021 (`net48`, основная), AutoCAD 2024 (`net48`), AutoCAD 2025 (`net8.0-windows`);
C#, WPF, MVVM; поставка — одна DLL `acadPaletteSetXDATA.dll`.

Документ описывает **что** и **в каком порядке** делать. Код в рамках этой задачи не пишется,
кроме уже выполненной замены имени RegApp (раздел 3, этап 0).

---

## 1. Термины

| Термин | Значение |
| --- | --- |
| **Схема** | Описания параметров (`PARAMETERS`), справочников (`ENUMS`) и шаблонов (`TEMPLATES`). |
| **JSON-схема** | Файл `schema.json` — редактируемая библиотека схемы вне чертежа. |
| **NOD-схема** | Копия схемы в словаре `VELEC` (Named Objects Dictionary) конкретного чертежа. |
| **XDATA объекта** | Значения параметров одного примитива в RegApp `BobrovXDATA`. |
| **VST** | Единое многоколоночное дерево (Virtual String Tree — аналог `TVirtualStringTree`): одна виртуализированная WPF-таблица-дерево, заменяющая всю вкладку «Свойства». |
| **Параметр** | Именованное значение объекта, описанное в схеме (`Power`, `Voltage`, …). |
| **ID параметра** | Неизменяемый ключ параметра (латиница, цифры, `_`). Используется в XDATA, шаблонах и `@@[...]`. |
| **Кэш** | Объектная модель, построенная однократным разбором NOD/XDATA; UI работает только с ней. |

Замечание о DXF/DWG: AutoCAD работает с DWG; словарь NOD, XRecord и XDATA одинаково сохраняются
в DWG и в DXF. Требование «DXF самодостаточен» в этом ТЗ означает: **чертёж (DWG или DXF) содержит
всю схему и не зависит от внешнего JSON**.

## 2. Анализ исходного ТЗ из задачи #17

### 2.1. Что логически связно и будет работать

1. Цепочка `JSON → NOD → XDATA → UI` корректна: схема одна на чертёж, значения — на объекте.
   Это устраняет дублирование описаний в каждом примитиве и укладывается в лимиты XDATA.
2. NOD сохраняется в DWG/DXF, переносится при `SAVEAS`, `DXFOUT/DXFIN`, поддерживает Undo.
3. Централизованные ENUM, на которые ссылаются параметры, и шаблоны-ссылки — правильная нормализация.
4. Требования производительности (однократный разбор, кэш схемы и значений) совпадают с уже
   реализованным подходом: чтение снимков в `Application.Idle`, UI работает с `ParsedEntityData`.
5. `CalculatedString` по уже загруженным значениям — дешёвая операция без обращения к базе.

### 2.2. Пробелы и противоречия, которые закрывает это ТЗ

| № | Проблема в исходном ТЗ | Решение в TZXDATA |
| --- | --- | --- |
| П1 | В XDATA нет ссылки на **шаблон**. Объект без значений нельзя отобразить: неизвестно, какие параметры у него должны быть. | В XDATA добавляется системное поле `TEMPLATE` (раздел 6). |
| П2 | `DEVICE_ID` не определён: это обозначение устройства или уникальный ключ? При `COPY`, `MIRROR`, `ARRAY`, вставке из буфера XDATA копируется вместе с ID — ID перестаёт быть уникальным. | `DEVICE_ID` — уникальный GUID объекта. Дубли обнаруживаются при чтении и исправляются командой (раздел 6.4). Пользовательское обозначение — обычный параметр схемы. |
| П3 | Параметр идентифицируется «именем/ID». Если отображаемое имя совпадает с ключом, переименование ломает данные всех объектов. | Разделены `Id` (неизменяемый ключ) и `Caption` (отображаемое имя). Переименование `Id` — только командой миграции. |
| П4 | Не описано поведение, когда XDATA содержит параметр, которого нет в NOD (удалён из схемы, объект скопирован из другого чертежа). | Значения **никогда не удаляются молча**. Показываются в группе «Не описаны в схеме» как строки (раздел 6.5). |
| П5 | Не описано, что хранится для ENUM: подпись (`220 В`) или ключ (`_AC_220V_50Hz`). | В XDATA хранится **ключ**. Подпись берётся из ENUM. Удалённый из ENUM ключ показывается с предупреждением. |
| П6 | Не описано слияние при повторном импорте JSON в чертёж, где уже есть схема и объекты. | Режимы импорта «Объединить» и «Заменить» с отчётом конфликтов (раздел 5.3). |
| П7 | `CalculatedString`: не определены циклы (`A → B → A`), ссылки на несуществующие параметры, формат чисел и ENUM в формуле. | Правила вычисления, диагностики циклов и форматирования (раздел 7). |
| П8 | Не указано, хранится ли результат `CalculatedString`. Внешние потребители (спецификация, выгрузка DXF без плагина) его не увидят. | По умолчанию не хранится. Флаг `Persist` записывает результат в XDATA при каждом изменении исходных параметров (раздел 7.4). |
| П9 | Лимиты AutoCAD не учтены: строка XDATA ≤ 255 байт, весь XDATA объекта ≤ 16 КБ, целое `1070` — 16 бит. | Типизированное хранение, проверка лимитов до записи, `1071` для `Integer` (раздел 6). |
| П10 | Существующие данные (материалы, `Тип/Номер/Название/Заголовок/Проект`, XML `VisualTreeString`, `ESMT_LEP_v1.0`) не имеют места в новой модели: таблица материалов — список строк, а не скалярный параметр. | Новый тип `Table` (табличный параметр с колонками из схемы) и команда миграции старых форматов (разделы 4.2, этап 9). |
| П11 | Имена: NOD — `VELEC`, RegApp — не указан; задача требует заменить `SMARTLINE` на `BobrovXDATA`. | RegApp — `BobrovXDATA`, корень NOD — `VELEC` (как в задаче). Оба имени — константы в одном месте Core. |
| П12 | Для `net48` нет встроенного `System.Text.Json`, а поставка — одна DLL без зависимостей. | JSON читается/пишется встроенными средствами .NET Framework (`DataContractJsonSerializer`) или собственным небольшим сериализатором в Core; новые DLL в поставку не добавляются. |
| П13 | Не описано групповое редактирование (уже реализовано на этапе 4) в новой модели. | «Разное» и запись одного поля во все объекты сохраняются для параметров схемы (раздел 8.5). |
| П14 | Изменение схемы, применение шаблона, импорт — изменения базы. Не указано Undo. | Все изменения NOD и XDATA — одна транзакция под именованной блокировкой, отменяются одним `U`. |
| П15 | Не указано, может ли объект содержать параметры вне шаблона и что происходит при смене шаблона. | Параметры вне шаблона допустимы (группа «Дополнительные»). При смене шаблона значения сохраняются (раздел 6.6). |

Вывод: исходное ТЗ работоспособно при условии решений П1–П15. Формат существующих чертежей
не ломается: новые данные пишутся в отдельный RegApp/NOD, старые читаются и мигрируют командой.

## 4. Схема параметров

### 4.1. Параметр (`PARAMETERS`)

| Поле | Обяз. | Описание |
| --- | --- | --- |
| `Id` | да | Уникальный неизменяемый ключ: `[A-Za-z_][A-Za-z0-9_]{0,63}`. Регистр не учитывается. Зарезервированы: `DEVICE_ID`, `TEMPLATE`, `FMT`. |
| `Type` | да | `String`, `Double`, `Integer`, `Boolean`, `Enum`, `CalculatedString`, `Table`. |
| `Caption` | да | Отображаемое имя (колонка «Параметр» в VST). |
| `Description` | нет | Подсказка (tooltip) и колонка «Примечание». |
| `Group` | нет | Группа в VST, например «Общие», «Электрика». Пусто — «Общие». |
| `Default` | нет | Значение по умолчанию; тип совпадает с `Type`. |
| `Enum` | для `Enum` | `Id` справочника из `ENUMS`. |
| `Format` | для `CalculatedString` | Строка формата, например `@@[GC_HeadDevice].@@[GC_HDGroup]`. |
| `Persist` | нет | Только `CalculatedString`: записывать результат в XDATA (по умолчанию `false`). |
| `Columns` | для `Table` | Список `Id` параметров-колонок (скалярные типы), например для материалов. |
| `Editor` | нет | Настройки редактора: `Unit` (ед. изм.), `Precision`, `Min`, `Max`, `MaxLength`, `ReadOnly`, `Multiline`, `AllowCustom` (для `Enum` — разрешить ввод значения вне списка). |

Добавление параметра или ENUM поддерживаемого типа выполняется только через схему,
**без изменения исходного кода**. Новый **тип** параметра требует кода: регистрируется
реализация интерфейса типа (разбор, форматирование, проверка, редактор VST) — см. раздел 10.

### 4.2. Тип `Table` (новый, для материалов)

Табличный параметр — упорядоченный список строк; колонки — параметры схемы.
Пример материалов из существующего интерфейса:

```text
Materials (Table)
    Columns: Mat_Category (Enum MaterialCategory), Mat_Mark (String),
             Mat_Count (Double), Mat_InSpec (Boolean), Mat_Comment (String)
```

Первая колонка-`Enum` (если отмечена `GroupBy`) группирует строки в VST, как курсивные
категории на текущем скриншоте. Сопоставление строк при групповом редактировании —
по ключевой колонке (`Key`, по умолчанию первая `String`-колонка; для материалов — `Mat_Mark`),
как в этапе 4.

### 4.3. Справочник (`ENUMS`)

| Поле | Описание |
| --- | --- |
| `Id` | Ключ справочника (`Voltage`, `Phase`). |
| `Caption` | Отображаемое имя справочника в редакторе. |
| `Items[]` | Упорядоченный список `{ Key, Caption }`. `Key` уникален в справочнике, хранится в XDATA. |

Один справочник используется любым числом параметров. Удаление справочника, на который
ссылается параметр, запрещено редактором (показывается список ссылающихся параметров).

### 4.4. Шаблон (`TEMPLATES`)

| Поле | Описание |
| --- | --- |
| `Id` | `DEVICE`, `CABLE`, `TRAY`, `MOTOR`, … |
| `Caption` | Отображаемое имя. |
| `EntityTypes` | Необязательный фильтр типов примитивов (`BlockReference`, `Polyline`, `Line`). |
| `Parameters[]` | Упорядоченные **ссылки** на `Id` параметров (не копии описаний). Необязательно `Default` — значение по умолчанию для этого шаблона, перекрывающее `Default` параметра. |

### 4.5. Проверки схемы (общие для JSON, NOD и редактора)

- уникальность `Id` в каждом разделе; допустимые символы; зарезервированные имена;
- каждая ссылка (`Enum`, `Columns`, `Parameters`, `@@[...]`) указывает на существующий объект;
- `Default` соответствует типу и, для `Enum`, существует в справочнике;
- нет циклов в `CalculatedString`; `Table` не содержит `Table` и `CalculatedString` с `Persist`;
- ошибки показываются списком «объект — поле — причина»; схема с ошибками не записывается в NOD.

## 5. JSON и NOD

### 5.1. Формат `schema.json`

```json
{
  "format": "BobrovXDATA.schema",
  "version": 1,
  "parameters": [
    { "id": "Device_Type", "type": "String", "caption": "Тип устройства", "group": "Общие" },
    { "id": "Power", "type": "Double", "caption": "Мощность", "default": 0,
      "editor": { "unit": "кВт", "precision": 2, "min": 0 } },
    { "id": "Voltage", "type": "Enum", "caption": "Напряжение", "enum": "Voltage",
      "default": "_AC_220V_50Hz" },
    { "id": "GC_Name", "type": "CalculatedString", "caption": "Обозначение",
      "format": "@@[GC_HeadDevice].@@[GC_HDGroup]" }
  ],
  "enums": [
    { "id": "Voltage", "caption": "Напряжение",
      "items": [ { "key": "_AC_220V_50Hz", "caption": "220 В" },
                 { "key": "_AC_380V_50Hz", "caption": "380 В" } ] }
  ],
  "templates": [
    { "id": "DEVICE", "caption": "Устройство",
      "parameters": [ "Device_Type", "Device_Class", "NMO_Name", "Power", "Current", "Voltage", "Phase" ] }
  ]
}
```

Кодировка UTF-8, числа — с точкой независимо от региональных настроек Windows.
Неизвестные поля JSON сохраняются при импорте в NOD и возвращаются при экспорте
(совместимость с будущими версиями).

### 5.2. Структура NOD

```text
NOD
└── VELEC                         DBDictionary
    ├── INFO                      Xrecord: версия схемы, дата/источник импорта, хэш
    ├── PARAMETERS                DBDictionary
    │   └── <Id параметра>        Xrecord: поле = значение (пары кодов 1/300 + типизированные 40/90/290)
    ├── ENUMS                     DBDictionary
    │   └── <Id справочника>      Xrecord: Caption + пары Key/Caption
    └── TEMPLATES                 DBDictionary
        └── <Id шаблона>          Xrecord: Caption, EntityTypes, список Id параметров
```

Одна запись — один объект схемы: редактирование одного параметра изменяет один Xrecord
(минимальный объём Undo, отсутствие лимита размера одного Xrecord на всю схему).
Длинные строки (`Description`, `Format`) разбиваются на фрагменты кода `300` без разрыва
Unicode-пар, как XML на этапе 5.

### 5.3. Команды

| Команда | Действие |
| --- | --- |
| `VELEC_SCHEMA_IMPORT` | Выбор `schema.json`, проверка (4.5), выбор режима: **Объединить** (добавить новые, обновить совпавшие по `Id`, ничего не удалять) или **Заменить** (схема чертежа = JSON). Перед записью — отчёт: добавлено/изменено/удалено, конфликты типов, параметры, удаляемые из схемы, но используемые объектами. Запись — одна транзакция, один шаг Undo. |
| `VELEC_SCHEMA_EXPORT` | Запись NOD-схемы чертежа в `schema.json`. Без изменения чертежа. |
| `VELEC_SCHEMA_EDIT` | Открывает редактор схемы (раздел 9). |
| `VELEC_TEMPLATE_APPLY` | Назначить шаблон выбранным объектам (также кнопкой на панели). |
| `VELEC_CHECK` | Проверка чертежа: дубли `DEVICE_ID`, параметры вне схемы, неизвестные ключи ENUM, превышение лимитов. Отчёт в командной строке/окне. |
| `VELEC_MIGRATE` | Перенос старых форматов (`ESMT_LEP_v1.0`, XML `VisualTreeString`, RegApp с прежним именем `SMARTLINE`) в формат `BobrovXDATA` v2 (этап 9). |
| `XDATAPALETTE` | Без изменений. |

Конфликт типа при «Объединить» (в чертеже `Power: String`, в JSON `Power: Double`) не применяется
автоматически: параметр помечается в отчёте, пользователь выбирает «оставить» / «заменить».
После импорта чертёж не зависит от JSON: все чтения выполняются только из NOD.

## 6. XDATA объекта (формат `BobrovXDATA` v2)

### 6.1. Содержимое

Только системные поля и значения. **Не хранятся** `Caption`, `Description`, списки ENUM,
настройки редактора и прочие метаданные.

```text
(1001 . "BobrovXDATA")
(1070 . 2)                                  ; FMT — версия формата XDATA
(1000 . "DEVICE_ID") (1000 . "3F2504E0-4F89-11D3-9A0C-0305E82C3301")
(1000 . "TEMPLATE")  (1000 . "DEVICE")
(1000 . "Device_Type") (1000 . "Щит")       ; String
(1000 . "Power")       (1040 . 2.5)         ; Double
(1000 . "Poles")       (1071 . 3)           ; Integer (32 бита)
(1000 . "InSpec")      (1070 . 1)           ; Boolean 0/1
(1000 . "Voltage")     (1000 . "_AC_220V_50Hz")  ; Enum — ключ
(1000 . "Materials") (1002 . "{")           ; Table: строки — вложенные списки
    (1002 . "{") (1000 . "Mat_Mark") (1000 . "CD35") (1000 . "Mat_Count") (1040 . 2.0) (1002 . "}")
(1002 . "}")
```

Пары «`Id` параметра (`1000`) + значение с кодом по типу». Порядок пар не важен.
Формат v1 (строки `ключ=значение`, этапы 3–5) отличается отсутствием `(1070 . 2)` первым значением.

### 6.2. Значения по умолчанию

Не заданное в объекте значение показывается из `Default` шаблона/параметра серым шрифтом
с отметкой «по умолчанию» и **не записывается** до явного изменения пользователем.
Команда/кнопка «Зафиксировать значения по умолчанию» записывает их явно (нужно, например,
для внешних программ, читающих только XDATA).

### 6.3. Лимиты и проверки до записи

- строка `1000` ≤ 255 байт UTF-8; `String` длиннее — ошибка проверки с указанием параметра
  (вариант на будущее — хранение длинного значения в XRecord ExtensionDictionary, раздел 10);
- суммарный XDATA объекта (все RegApp) ≤ 16 КБ — проверяется по оценке размера до `Commit`;
- `Integer` — `1071`; `Boolean` — `1070` (0/1); `Double` — `1040`;
- нарушение у любого объекта группы — отказ всей операции, как на этапе 5.

### 6.4. `DEVICE_ID`

GUID, создаётся при назначении шаблона. Служит ключом для будущих связей между объектами.
При чтении выделения/чертежа дубли (результат `COPY`, `ARRAY`, вставки из буфера) отмечаются
предупреждением в VST; `VELEC_CHECK` предлагает создать новые GUID у копий (объект с меньшим
handle сохраняет исходный ID). Автоматическая перегенерация при копировании — необязательное
развитие (через `Database.ObjectAppended`/`DeepCloneEnded`), не входит в первую очередь.

### 6.5. Данные вне схемы

- `Id` есть в XDATA, нет в NOD → группа «Не описаны в схеме», значение как строка, доступно
  удаление. При импорте схемы с этим параметром значение снова становится типизированным.
- ключ ENUM отсутствует в справочнике → показывается ключ с предупреждением.
- тип значения в XDATA не совпадает с типом схемы → значение показывается как строка с
  предупреждением; запись нового значения приводит его к типу схемы.

### 6.6. Шаблон объекта

- Объект без `TEMPLATE`, но с `BobrovXDATA` — показываются только заданные значения.
- Смена шаблона не удаляет значения: параметры вне нового шаблона переходят в группу
  «Дополнительные»; их удаление — отдельное явное действие.
- Пользователь может добавить к объекту параметр схемы вне шаблона (кнопка «Добавить параметр»).

## 7. `CalculatedString`

### 7.1. Синтаксис

`@@[Id]` — подстановка значения параметра того же объекта. `@@@@` — литерал `@@`.
Остальной текст выводится как есть.

```text
GC_HeadDevice = "ЩУ1", GC_HDGroup = "3", Format = "@@[GC_HeadDevice].@@[GC_HDGroup]"  →  "ЩУ1.3"
```

### 7.2. Подставляемое значение

- `String` — как есть; `Enum` — `Caption` элемента (ключ — через `@@[Id:key]`);
- `Double` — с `Editor.Precision`, десятичный разделитель — текущей культуры AutoCAD
  (решение по умолчанию; альтернатива — фиксированный, задаётся в `INFO` схемы);
- `Integer` — как есть; `Boolean` — «Да»/«Нет»;
- `CalculatedString` — рекурсивно; отсутствующее значение — значение по умолчанию, иначе пусто.

### 7.3. Вычисление и пересчёт

- Формулы разбираются **один раз** при загрузке схемы в кэш: список фрагментов и
  граф зависимостей (`Id` → зависимые `CalculatedString`). Циклы выявляются при проверке схемы.
- Вычисление — по значениям кэша объекта, **без повторного чтения XDATA**.
- Изменение параметра в VST сразу пересчитывает только зависимые строки (по графу).
- Ссылка на несуществующий параметр — `@@[Id]` остаётся в тексте, строка отмечается ошибкой.
- При множественном выделении результат вычисляется для каждого объекта; различие → «Разное».
- `CalculatedString` в VST только для чтения.

### 7.4. `Persist`

Если `Persist = true`, результат записывается в XDATA в той же транзакции, что и изменение
исходного параметра, а также командой `VELEC_CHECK` (пересчёт всего чертежа).
Значение в XDATA для таких параметров — производное: при чтении используется вычисленное.

## 8. Вкладка «Свойства» — единый VST

### 8.1. Компоновка

Вся вкладка «Свойства» — одна многоколоночная таблица-дерево. Отдельные `TextBox`, `Expander`
«ССЫЛКА НА ПРОЕКТ» и таблица «МАТЕРИАЛЫ» удаляются: эти данные становятся параметрами схемы
и строками VST. Над деревом **обязательно резервируется панель кнопок управления**.

```text
┌───────────────────────────────────────────────────────────────┐
│ [Шаблон ▾ DEVICE] [+ Параметр] [⟳] [⊞/⊟] [Фильтр…] [Схема] [»]│  ← панель управления (резерв, высота 32 px)
├────┬────────────────────┬──────────────────┬───┬──────────────┤
│    │ ПАРАМЕТР           │ ЗНАЧЕНИЕ         │ ● │ ПРИМЕЧАНИЕ   │  ← заголовок колонок
├────┼────────────────────┼──────────────────┼───┼──────────────┤
│    │ ▾ Общие            │                  │   │              │
│    │   Тип устройства   │ Щит              │ ● │              │
│    │   Обозначение      │ ЩУ1.3            │ ƒ │ вычисляемое  │
│    │ ▾ Электрика        │                  │   │              │
│    │   Мощность, кВт    │ 2,50             │ ● │              │
│    │   Напряжение       │ 220 В          ▾ │ ○ │ по умолчанию │
│    │   Фаза             │ Разное         ▾ │ ● │              │
│    │ ▾ Материалы        │ 10 строк         │   │ [+ Добавить] │
│    │   ▾ Линейная арм.  │                  │   │              │
│ ×✎ │     CD35           │ 2                │ ☑ │ Пример       │
│ ×✎ │     CS 10.3        │ 1                │ ☑ │              │
│    │ ▸ Не описаны в… (1)│                  │ ! │              │
└────┴────────────────────┴──────────────────┴───┴──────────────┘
```

### 8.2. Колонки

| № | Колонка | Скалярный параметр | Строка `Table` (материал) | Узел группы |
| --- | --- | --- | --- | --- |
| 0 | Действия (узкая) | пусто | `×` удалить, `✎` редактировать | пусто |
| 1 | **Параметр** (дерево, отступы, ▸/▾) | `Caption` (+ ед. изм.) | ключевая колонка (Марка) | имя группы/категории (курсив) |
| 2 | **Значение** | редактор по типу | вторая колонка (Кол.) | счётчик строк |
| 3 | **●** (узкая, состояние/флаг) | `●` задано, `○` по умолчанию, `ƒ` вычисляемое, `!` ошибка | `Boolean`-колонка (В спецификацию) | пусто |
| 4 | **Примечание** | `Description` / сообщение проверки | колонка комментария | кнопка `+ Добавить` |

Сопоставление колонок таблицы с колонками VST задаётся в схеме (`Editor.VstColumn` колонок `Table`).
Ширины колонок изменяются перетаскиванием и сохраняются в настройках пользователя; колонки 0, 3
и 4 скрываются через контекстное меню заголовка. При узкой панели — горизонтальная прокрутка.

### 8.3. Редакторы ячейки «Значение»

`String` — текст; `Double`/`Integer` — текст с проверкой числа, `Min/Max`, ед. изм.;
`Boolean` — флажок (три состояния при «Разное»); `Enum` — выпадающий список подписей
(с вводом при `AllowCustom`); `CalculatedString` — только чтение; `Table` — дочерние строки.
Редактор создаётся только для ячейки в фокусе (виртуализация).

### 8.4. Панель управления (резерв сверху)

Обязательный набор первой очереди; остальные места — резерв под будущие кнопки:

| Кнопка | Действие |
| --- | --- |
| Шаблон ▾ | Показывает шаблон выделения («Разное» при различии); выбор — `VELEC_TEMPLATE_APPLY`. |
| + Параметр | Добавить к выделению параметр схемы вне шаблона. |
| ⟳ | Пересчитать `CalculatedString` / перечитать выделение. |
| ⊞/⊟ | Развернуть/свернуть все группы. |
| Фильтр | Поиск по `Caption`/`Id`/значению; скрывает несовпавшие строки. |
| ⚙ Схема | Открыть редактор схемы; в меню — импорт/экспорт JSON. |
| » | Меню переполнения при узкой панели. |

Список выбора объекта и строка статуса над вкладками (этап 3) сохраняются.

### 8.5. Поведение (перенос этапов 3–5)

- нет выделения — VST неактивен и пуст; выделение без `BobrovXDATA` — пустые параметры и
  предложение «Назначить шаблон»;
- множественное выделение: строки — объединение параметров; совпавшие значения показываются,
  различающиеся/отсутствующие — плейсхолдер **«Разное»** (курсив, серый);
- Enter/выход из ячейки записывает **только** изменённый параметр во все объекты одной
  транзакцией; флажок применяется щелчком; `+ Добавить` / `×` — для строк `Table` во всём наборе;
- ошибки записи откатывают группу и показываются над VST; Undo/Redo — нативные;
- состояние раскрытия групп и позиция прокрутки сохраняются при смене выделения того же шаблона.

## 9. Редактор схемы

Модальное WPF-окно (`Application.ShowModalWindow`), открывается командой `VELEC_SCHEMA_EDIT`
и кнопкой «⚙ Схема». Палитра для этого слишком узкая.

- **Параметры:** список с поиском; форма полей раздела 4.1; редактор формулы с подсказкой
  `@@[...]` и предпросмотром на выбранном объекте; список шаблонов, использующих параметр.
- **ENUM:** список справочников; таблица `Key`/`Caption` с добавлением, удалением, порядком;
  запрет удаления используемого ключа без подтверждения (показывается число объектов).
- **Шаблоны:** список шаблонов; два списка «Все параметры» ⇄ «Параметры шаблона» с порядком,
  переопределением `Default`, фильтром типов примитивов.
- **Импорт / экспорт JSON** — те же операции, что команды раздела 5.3.
- Изменения копятся в черновике окна; «Применить» — проверка (4.5) и одна транзакция NOD
  (один шаг Undo); «Отмена» — без изменений чертежа.

## 10. Производительность и кэш

1. **Кэш схемы** — один на документ. Строится из NOD при первом обращении, содержит словари
   по `Id`, разобранные формулы и граф зависимостей. Сбрасывается при изменении объектов
   словаря `VELEC` (`Database.ObjectModified` с фильтром по ObjectId словарей), импорте, Undo/Redo
   NOD и смене документа.
2. **Кэш значений** — `ObjectId → ObjectValues` (типизированные значения, шаблон, `DEVICE_ID`,
   предупреждения). XDATA каждого объекта разбирается **один раз** при выборе. Запись
   инвалидирует только изменённые объекты; Undo/Redo/внешние команды — через существующее
   перечитывание после `CommandEnded`. Размер ограничен (LRU, например 10 000 объектов).
3. VST и другие интерфейсы читают только кэш; обращение к параметру — поиск в словаре.
4. Объединение множественного выделения — O(объекты × параметры), без обращения к базе.
5. VST виртуализирован (`VirtualizingStackPanel`, `Recycling`): создаются элементы только видимых строк.
6. Критерии: выделение 1 000 объектов × 50 параметров — построение VST ≤ 300 мс после
   чтения снимков; повторный выбор того же набора — без разбора XDATA (проверяется счётчиком
   разборов в тестах); трассировка времени — существующий `XDATAPALETTE_TRACE=1`.

## 11. Расширяемость

- Тип параметра — реализация интерфейса (условно `IParameterType`: разбор XDATA/JSON/NOD,
  форматирование, проверка, фабрика редактора VST), регистрируемая в одном реестре.
  Неизвестный тип из более новой схемы показывается как строка только для чтения.
- Новые поля схемы — новые пары в Xrecord/JSON; старые версии плагина их сохраняют (5.1).
- `FMT` в XDATA и `version` в `INFO`/JSON позволяют менять форматы с миграцией.
- Возможные развития без изменения формата существующих чертежей: ссылки между объектами
  по `DEVICE_ID` в формулах, длинные значения в XRecord ExtensionDictionary, вычисляемые
  числовые выражения, спецификация по шаблонам и колонке «В спецификацию».

Принцип: **JSON — редактируемая библиотека схемы, NOD — схема конкретного чертежа,
XDATA — значения конкретных объектов, VST — представление кэша.**

```text
schema.json  ── VELEC_SCHEMA_IMPORT ──▶  NOD «VELEC» ── кэш схемы ──────────────┐
schema.json  ◀── VELEC_SCHEMA_EXPORT ──  NOD «VELEC»                            ├──▶  VST / спецификация
                                         XDATA «BobrovXDATA» ── кэш значений ───┘
```

## 12. Этапы реализации

Каждый этап — отдельная задача/PR с автотестами и, для UI, рендерами в CI (`wpf-renders`).
Этапы 1–4 не зависят от AutoCAD и тестируются на Linux/Windows без него.

### Этап 0. Переименование RegApp — **выполнен в задаче #17**

- `SMARTLINE` → `BobrovXDATA` в коде, тестах, примерах, документации; тест на разбор `BobrovXDATA`.
- **Приёмка:** `grep SMARTLINE` по коду пуст; все unit-тесты проходят.

### Этап 1. Модель схемы и JSON (Core)

- Классы параметра/ENUM/шаблона, типы `String`…`Table`, проверки раздела 4.5.
- Чтение/запись `schema.json` без внешних DLL (`net48` и `net8`), сохранение неизвестных полей.
- Пример `examples/schema.json` (DEVICE, CABLE, TRAY, MOTOR; Voltage, Phase; материалы).
- **Приёмка:** round-trip JSON → модель → JSON без потерь; тесты всех ошибок проверки.

### Этап 2. Хранение схемы в NOD и команды импорта/экспорта

- Сериализация модели в `VELEC/INFO|PARAMETERS|ENUMS|TEMPLATES` (через абстракцию записей,
  как `EntityDataSnapshot`, чтобы тестировать без AutoCAD).
- `VELEC_SCHEMA_IMPORT` (Объединить/Заменить, отчёт), `VELEC_SCHEMA_EXPORT`; кэш схемы.
- **Приёмка:** импорт → сохранение DWG и DXF → открытие без JSON → экспорт даёт эквивалентную
  схему; импорт отменяется одним `U`; ручной сценарий в `docs/autocad-verification.md`.

### Этап 3. Формат XDATA v2 и кэш значений

- Разбор/запись раздела 6, проверки лимитов, `DEVICE_ID`, `TEMPLATE`, данные вне схемы.
- Кэш значений и счётчик разборов; `XDataPatch` для v2 (одно поле / строка `Table`);
  `XDataWriter` без изменения транзакционной модели.
- **Приёмка:** тесты round-trip всех типов, лимитов 255 байт/16 КБ, сохранения посторонних
  RegApp, отсутствия повторного разбора; групповая запись одного поля сохраняет остальные.

### Этап 4. `CalculatedString`

- Разбор формул, граф зависимостей, обнаружение циклов, форматирование (раздел 7), `Persist`.
- **Приёмка:** `ЩУ1` + `3` → `ЩУ1.3`; цикл и неизвестная ссылка дают диагностику;
  изменение исходного параметра пересчитывает только зависимые; без чтения XDATA.

### Этап 5. VST: отображение (только чтение)

- Новый `UserControl` вкладки «Свойства»: панель управления сверху (резерв, кнопки ⟳, ⊞/⊟,
  фильтр), VST с колонками раздела 8.2, группы, `Table`-строки, состояния `●/○/ƒ/!`, темы.
- Удаление `PropertyEditorView` и жёстко заданных полей/списков.
- **Приёмка:** WPF smoke для net48/net8 в обеих темах; виртуализация (видимых контейнеров
  меньше числа строк); рендеры `tzxdata-stage5-*.png`.

### Этап 6. VST: редактирование и групповое редактирование

- Редакторы раздела 8.3, «Разное», Enter/выход из ячейки, флажки, `+ Добавить`/`×`/`✎` для `Table`,
  «+ Параметр», запись через `XDataWriter`, мгновенный пересчёт формул.
- **Приёмка:** перенесённые тесты этапа 4 (`GroupEditingTests`) для v2; ручная проверка Undo/Redo.

### Этап 7. Шаблоны на объектах

- Кнопка/команда `VELEC_TEMPLATE_APPLY`, создание `DEVICE_ID`, смена шаблона (6.6),
  значения по умолчанию шаблона, «Зафиксировать значения по умолчанию».
- **Приёмка:** назначение шаблона группе — одна транзакция; значения вне шаблона сохраняются.

### Этап 8. Редактор схемы

- Окно раздела 9: параметры, ENUM, шаблоны, импорт/экспорт, черновик и «Применить».
- **Приёмка:** создание параметра/ENUM/шаблона без изменения кода сразу доступно в VST;
  запрет удаления используемых объектов; один шаг Undo на «Применить».

### Этап 9. Миграция и проверка чертежа

- `VELEC_MIGRATE`: `ESMT_LEP_v1.0`, v1 `BobrovXDATA` (`ключ=значение`), XML `VisualTreeString`
  и RegApp с прежним именем `SMARTLINE` → v2; таблица соответствия (`Type → Device_Type`,
  `Material → Materials`, …) задаётся в схеме, исходные данные удаляются только по флагу.
- `VELEC_CHECK`: дубли `DEVICE_ID`, данные вне схемы, ключи ENUM, лимиты, пересчёт `Persist`.
- **Приёмка:** `examples/stage3-selection.lsp` после миграции показывает те же значения и
  материалы в VST; повторная миграция ничего не меняет.

### Этап 10. Производительность, документация, выпуск

- Нагрузочный тест кэша/объединения (раздел 10, п. 6), обновление README и `docs/`,
  ручной сценарий AutoCAD 2021, выпуск одной DLL через существующий Release.
- **Приёмка:** критерии раздела 10 выполнены; CI зелёный; DLL без новых зависимостей.
