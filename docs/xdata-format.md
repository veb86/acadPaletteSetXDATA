# Форматы XDATA/XRecord (чтение этапа 3, запись этапов 4–5)

ТЗ задаёт названия RegApp (`ESMT_LEP_v1.0`, `BobrovXDATA`) и поля UI, но не формат их сериализации.
Ниже определён воспроизводимый контракт для проекции полей. Совместимость с произвольными
данными этих приложений не предполагается: все неизвестные значения остаются в дереве.

## XDATA

Читаются все RegApp из `Entity.XData`, включая сторонние. Код `1001` начинает ветку
приложения; `1002` со значениями `{` и `}` создаёт вложенный список. Остальные DXF-коды
и значения сохраняются в узлах, числа форматируются независимо от региональных настроек,
бинарные значения отображаются в HEX. Строка `1000` перед `{` служит именем группы.

Для `ESMT_LEP_v1.0` и `BobrovXDATA` строки `1000` вида `ключ=значение` заполняют поля:

| Ключ | Русский псевдоним | Назначение |
| --- | --- | --- |
| Type | Тип | Тип объекта |
| Number | Номер | Номер |
| Name | Название | Название |
| Title | Заголовок | Заголовок |
| ProjectReference | Проект | Ссылка на проект |

Имена ключей и RegApp сравниваются без учёта регистра. Разделение выполняется по
**первому** `=`, остальные символы значения сохраняются. Позиционные строки,
JSON, бинарные форматы и другие соглашения не преобразуются в поля UI.

Группа `Material` / `Материал` содержит строки с ключами `Category`, `Name`, `Count`,
`IsInSpec`, `Comment`. Псевдонимы: `Категория`, `Марка`, `Количество`, `ВСпецификацию`,
`Примечание`. `IsInSpec` принимает `true` / `false` / `1` / `0`; отсутствующий или
неизвестный флаг отображается как nullable-состояние. Это не вычисление «Разное».
Количество сохраняется строкой, включая `1,2`.

## ExtensionDictionary / XRecord

Сервис рекурсивно читает все XRecord в словаре самого выбранного примитива, включая
вложенные словари. Имена показываются полными путями. Данные определения блока,
ссылки/handles из значений, внешние файлы и другие объекты базы автоматически не обходятся.
Динамический блок читается как выбранный `BlockReference`.

Любой XRecord сохраняется как последовательность DXF-кодов/значений. Если **все**
значения являются строками кода `1` или `1000`, они объединяются по порядку.
XML дополнительно преобразуется в дерево элементов/атрибутов; сырой буфер также виден.
Только корень `VisualTreeString` включает проекцию в поля/материалы:

```xml
<VisualTreeString>
  <Properties>
    <Type>Кабель</Type>
    <Number>022</Number>
    <Name>Кабель</Name>
    <ProjectReference>Проект 021</ProjectReference>
  </Properties>
  <Materials>
    <Material Category="Линейная арматура" Name="CD35" Count="2"
              IsInSpec="true" Comment="Пример" />
  </Materials>
</VisualTreeString>
```

Поля `Properties` и `Material` допускают атрибуты или дочерние элементы.
Структурные XML-имена `VisualTreeString`, `Properties`, `Materials`, `Material`
используйте как в примере. При дублировании полей последнее прочитанное значение
побеждает: сначала XDATA в порядке буфера, затем XRecord в порядке обхода словаря.
Материалы собираются из обоих источников без удаления дублей. Неизвестные XML-узлы
сохраняются, но не получают выдуманного значения в UI.

## Ошибки, пределы и выбор нескольких объектов

Ошибки скобок восстанавливаются на следующем RegApp; неверный XML не мешает чтению
следующего XRecord. Предупреждения доступны на вкладке «XDATA». Данные за пределами
ограничений пропускаются с предупреждением: 16 384 значений на буфер, глубина списка/XML
64, XML до 1 048 576 символов и 16 384 узлов чтения, словарь до глубины 32 / 4096
посещённых словарей / 4096 XRecord. DTD и внешние XML-сущности запрещены.

Каждый выбранный примитив имеет отдельный снимок/дерево. Список над вкладками выбирает
объект для просмотра дерева. Поля «Свойства» объединяют всё выделение, вычисляют «Разное»
и позволяют записать подтверждённое поле в каждый объект. Правила сопоставления материалов,
сохранения неизвестных данных и ограничений записи — в [group-editing.md](group-editing.md).
Ошибка чтения или пустой набор очищает предыдущие данные.
